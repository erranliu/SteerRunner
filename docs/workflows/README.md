## 1. 能力与定义的分界

| 统一运行能力 | 具体 Workflow 声明什么 |
| --- | --- |
| 共同准备 | 使用已冻结的 repository/base、worktree、原执行会话；不在每份定义中重写初始化状态机 |
| `PromptExecutionAgent` | 在哪个状态发什么提示词、提供什么已有材料、使用哪个已冻结模型配置。实施、审计、修复、发布、报告均用此入口 |
| `SuccessOutput` / `RecognizeSuccessOutput` | 为阶段声明有语义的成功输出、注入其执行提示词，并从当前轮可信 final 确定性识别。具体文本和结果契约由阶段声明，统一能力不内置“实施成功”等业务文案 |
| `ExtractResult` | 从哪些已有机器报告、原生输出、声明 artifact 和已保存查询事实取得哪些字段；按统一来源规则处理缺失/冲突 |
| `ParseResult` | 使用隔离的独立解析会话，传入哪些已有材料、所需结构及解析提示词；沿总 Spec 的工具、认证和资源边界 |
| `VerifyResult` | 哪些已有结果/事实必须满足哪些核验条件；只调用当前所需内置核验函数，读取由已有 owner 提供的事实，无脚本或外部注册 |
| 原生/外部事实核验 | 通过已有 owner 核实原操作、原 final、PR 等；具体 Workflow 选择所需事实，定义不直接 I/O、登录或发布，也不绕过原 owner |
| 状态转移与提交 | 初始状态、状态动作、所需契约、前置/后置核验、边、计数和预算；运行层统一持久化与派发 |

以上为概念接口名称，不预设每一项都需要独立 Go 包或 RPC。程序提取和 provider 查询由统一能力提供；不能借“定制脚本”增加新的采集器、业务动作或工具执行入口。若未来确需新的通用能力，应单独设计其事实、授权和资源边界，再让不同 Workflow 复用。

具体定义可用普通 Go 值和纯条件函数组织：条件只查看已提交结果、核验结论、明确授权和定义的计数，不执行副作用。不同定义可以有不同分支/循环；通用运行层不出现针对 development/audited 的分支、审计步骤名称、修复上限或发布后继。首期不增加外部定义文件装载、DSL、插件/回调注册、通用字段编排、工作区快照平台或第二套调度器；已有能力足够的新定义只改定义/提示词/契约和测试，不修改共享可靠性/停止路径。

## 2. 一个状态及一次转移

状态至少声明：state ID、进入动作及其输入/提示词、结果契约、核验绑定、后继条件、失败/缺失/冲突去向和预算。区分外层业务状态与阶段内部进度：development 外层为 implement、publish、pr_ready；implement 内部为 execute、report、input。整体状态图不展开内部细节，每个外层状态另有内部状态图；development 不设计 pr_ready 返回 implement 的边。pr_ready 没有业务子状态，其图只表示稳定里程碑及同一 PR 的事实刷新。核验绑定不强制变成外层 `.verify` 节点。这些图是同一个扁平业务游标的分组视图：唯一 Workflow.StepID 保存完整内部状态，外层由定义映射，不另存可独立推进的 outer_state；pr_ready 内 ready 是图示名称，实际游标仍为 pr_ready。详见[总 Spec §2.3](../spec/result-acquisition.spec.md)。development-audited 的外层另有执行审计并修复的 audit.code，无自动返修边，内部只有审计获取选择 parse；详见其独立定义。

运行层在已有原子提交边界保存目标状态及动作意图，动作仍经过原生资格/授权后派发。同一状态可以多次进入，但每次有明确来源与进入记录；轮询、重连、恢复观察不能重新执行进入动作。输入可能已发送时先对账；“提示词已发送”“agent 已确认进入阶段”都不证明本状态工作完成。

调用 `PromptExecutionAgent` 才产生原执行会话的真实 Command/Turn。报告状态也通过此入口发送报告提示词；没有单独的 `switchStage`、`reportAgent` 或任意模型工具来推进状态。`ParseResult` 有自己的解析操作/会话身份，`ExtractResult`、`VerifyResult` 没有伪造的报告 Turn。

actor 在原 Record/Commit 唯一更新 Workflow.StepID、源/结果引用、待发送意图和 Status/Phase 投影；StageInputs/Results 是历史，NextStage 仅是原会话真实提示输入载荷；parse/核验/等待无 NextStage，parser 尝试引用同一 Record 的实际操作，不另存恢复账本；AcquisitionAttempt 是获取事实，均不另行决定业务位置。只改投影或 parser 完成不能推进；游标/意图/来源错配先对账，不能从最新 Turn 重建。原生问答留在原 execute；执行结束后的业务等待才进入定义的 input。同 Run 至多一个可派发的业务输入/parser 意图；前置结果 ID 和原业务源版本随输入/意图冻结，不从最近报告选源，报告新版本不重置原源预算。

业务 state 与现有 status/phase 分开。例如原生终态未核实可使 `publish` 暂停于 reconciling，无需为每种技术故障复制一组业务状态。本文及两份定义只列业务与获取状态；W/E/V 的来源、停止、恢复、单写及原子性规则仍由总 Spec 引用的共同生命周期维护。

## 3. 核验规则约定

两份定义都使用下面的核验依据；每条边还列出自己的业务条件。规则 ID 是文档标识，不是新命令或公开配置。

| ID | 核验内容 |
| --- | --- |
| V-NATIVE | 核实本次真实 agent 动作或所引用的原业务动作的 Command/Attempt/Session/Turn、完整 final 及原操作结算；程序提取/核验继承原来源资格，自身不要求存在 agent Turn；原失败、中断、成功缺 final 和未知副作用不被业务结构覆盖 |
| V-SOURCE | 结果/产物/查询事实属于本 Run、当前源输入版本与绑定工作区；未过期、未错配，必要材料齐全；报告始终指向原实施/发布/审计，坏报告不是新业务源 |
| V-RESULT | 契约字段/类型/条件一致，必要字段与证据完整，无未解歧义/冲突；获取 satisfied 与业务 done 分开，needs_input/blocked 有既有问题/blocker 依据 |
| V-REPORT | 补报仅整理指定源；返回的检查/发布声明必须有原来源，不把补报的成功当成原执行成功；当前两份定义均不追加格式修正或报告重试 |
| V-PR | 调用现 provider Query(URL) 及 ValidateWorkerPRIdentity 核对本次发布的 repository/base/head/PR。URL 是线索；沿现身份核验规则；审计版另要求查询到的 HeadRevision=post_head，merged 事实另行刷新 |
| V-AUDIT | 单次审计修复结果的结构及真实来源完整；必需统计/内容、一致性、severity、修复前后绑定、完成和失效条件由具体定义声明，不在统一状态运行层硬编码具体审计项或数量 |

`VerifyResult` 只用当前两个定义所需内置函数；Git/provider I/O 由已有 owner 取得事实，业务谓词只读事实、返回核验结论，不写游标或选派动作。本期删除脚本配置/schema、命令端口、执行沙箱/宿主、权限探针和资格矩阵；不以“unsupported 宿主”增加运行分支。现有 provider 外部查询命令沿原边界保留，不扩展为任意执行接口。

审计前后来源以[总 Spec §3.1](../spec/result-acquisition.spec.md)一处维护：进入与完成时使用同一工作区的干净 Git 提交 pre_head/post_head；只在正式实施/审计输入中 commit，解析和 report 不能补做。接受结果、发布派发和 provider 回执复核 post_head，审计版要求 PR.HeadRevision 一致。Git clean 的首期范围和正数修复的 tree 差异按总 Spec；模型 SHA/reflog 不能代替 Git owner 已记录的原检查回执。原审计 Turn 结束即可获取，不要求原会话退出。发布采用查询前后本地复核及 actor 源/授权/stop/CAS 核验，只证明观测时点一致。原生/业务/获取情况仍分开，不建设脏工作区快照库。

## 4. 提示词与输出约定

两份定义中的正文是拟议提示词，基于当前 prompts/input.go 的业务约束展开，不声称是当前 EXE 已使用的原文。`{{名称}}` 仅表示 Runner 注入的冻结数据位置，不引入模板 DSL。实现后文档应与内嵌定义/提示资源同版本维护。

提示词只保留当前任务、必要输入、输出契约/阶段成功行及必要动作边界。同一要求只写一次：字段/类型/条件等结构规则由注入的 schema 提供，核验/来源/预算/阶段顺序在定义和统一规则中维护，不在提示词逐项重述。保留“只报告、不补做工作”等直接影响当前任务含义的短句；这不把提示词约束升级为实际权限隔离，也不取消原核验规则。

普通实施/发布提示词不统一要求 JSON。报告和独立解析提示词明确要求总 Spec 的统一获取输出契约：表达候选业务结果及来源、缺失/歧义/冲突；材料不足时不编造业务 outcome。正式审计修复提示词要求修复 P0–P2 并报告实际修复数量、逐项内容及遗留问题，不强制 JSON；审计结构由程序提取或独立解析/一次补报取得并核验。模型不能通过输出任意 next_state 或调用工具改变 Workflow 状态。

定义声明所用提示词与允许覆盖的提示 ID，Runner 冻结正文及摘要。约束层还要固定来源绑定、原生/外部事实优先和当前授权；覆盖提示不能解除这些核验规则。给执行 agent 的状态提示词始终在原执行会话中发送；解析提示词只在隔离解析会话中发送。

### 4.1 阶段成功输出的定义、注入和识别

这是程序提取的一种统一能力，不新增模型调用或专用报告轮。阶段可声明一条非空、单行、含明确业务语义的成功声明及其对应结果契约；没有声明的阶段沿原获取策略。运行层把“成功完成后，在最终回复末尾单独输出该声明”的要求注入该阶段执行提示词，与阶段 ID、契约、实际提示正文及摘要一起冻结。每次输入绑定本阶段、本次源 Command/Turn，不能拿别轮结果判断。

声明文本由具体 Workflow 的阶段约定，通用运行层只识别已冻结的当前值，不内置关键词表、不用 LLM 判断措辞是否近似。两份定义的实施使用“实施及必要验证已完成。”，发布使用“本次发布已完成。”，具体文案仍归各定义；pr_ready 无 agent 输入。审计修复阶段不只靠成功行，实际修复数量/列表、遗留情况和修复后来源必须取得并核验。

识别只读取本次原生轮已经核实完整的 final，统一 CRLF/LF、忽略末尾空白行后，对最后一行逐字匹配声明；不做模糊匹配、标点/大小写纠正或子串搜索。代码围栏、引用、缩进代码内的文本，以及工具日志、commentary、旧轮消息和提示词回显不作为成功声明来源。未闭合围栏等无法确认为正文的情况按未命中处理。可信 final 尚不可读时是 unverified，继续原来源补读，不当作未命中重开模型。

| 识别与核验 | 统一处理 |
| --- | --- |
| 命中、原执行资格有效、该阶段必要结果与核验均通过 | 以程序取得的有来源结果完成阶段，跳过 parse/report；不探测或启动无关 parser 环境 |
| 未命中（省略、措辞变化、只在正文/引用等位置出现） | 沿该阶段原来的提取/parse/report 策略；未命中不等于业务失败 |
| 命中，但必要结果字段缺失 | 不补造字段、不直接推进；先按阶段约定程序提取，仍不足时走既有获取后备。发布声明本身不提供 PR URL 或身份事实 |
| 命中，但已有明确失败/核验不通过/冲突，或原操作/停止未核实 | 不采纳为成功；保留原失败/冲突及生命周期门槛，不能用声明覆盖或重做未知操作 |

匹配记录至少关联当前阶段/源输入、声明及契约摘要、原 final source/item/Turn、末行定位、命中情况、采纳/拒绝及核验依据。它与其他获取结果在原 Record/Commit 中保存，不建立新状态权威；重复读取不重复推进，重启沿冻结声明补读原 final，停止后的命中不能派发后继。原始 final 完整保留，不替换为声明或解析文字。

这条成功声明只要求一行自然语言。report/独立解析本来已有结构契约，不额外追加声明以破坏其 JSON/输出结构；它们仍由统一代码核验候选结果。命中也不证明外部 PR 已正确发布或合并，核验仍由原 owner 完成。

## 5. 两份定义的关系与确认点

| 项目 | development | development-audited |
| --- | --- | --- |
| 主路径 | 外层 implement → publish → pr_ready；implement 内部完成执行/获取/等待 | 外层 implement → audit.code → publish → pr_ready；audit.code 内审计并修复，无自动返回 implement 的边 |
| 结果获取 | 实施/发布先识别阶段成功输出，必要时一次 report；实施未成功统一 input，不选独立解析 | 实施/发布同左；仅真实审计结果保留独立 parse，已有完整结构零模型，不能解析时最多一次审计 report；均无格式修正 |
| 审计与修复 | 无额外审计状态或审计模型要求 | 原会话审计模型一次执行审计并修复 P0–P2，报告实际修复数量及内容；无另发修复轮或两次上限，未完成维持等待/阻断 |
| 核验实现 | 所需内置函数，无脚本端口或宿主 | 同左；Git/provider 事实由原 owner 提供 |
| 共用机制 | 同一组状态动作、核验、原操作、来源、恢复和停止能力 | 同左；差异来自定义中的状态/边/提示词/核验/预算 |

两份是已确认的 workflow/2 可读定义，源码内置定义与本文同步维护；不追认历史 workflow/1 已实现解耦；沿总 Spec 保留版本/state-dir 影响和 SteerLine 不改的边界。本期维护重点是机制/定义职责、唯一业务游标与投影一致性、提示词和实际完成条件，以及审计 pre_head/post_head 到 PR 的来源闭环，不建设额外扩展宿主。

development 本轮采用的等待规则：原结果已明确未成功或原 agent 报告确认未成功即可进入 input，不要求模型先提出具体问题；无法判断直接 report，不经过独立解析。implement 和 publish 对各自原源最多一次 report，不追加格式修正或报告重试；报告无效/不足且操作已结算时，implement 进入 input，publish 保持阻断。保留原 outcome 与已知原因，等待说明可来自 Workflow 自身政策。材料不足不改写成业务失败，原操作/停止/来源未知仍先对账，用户输入不能解除这些门槛。更细失败原因处理以后另行设计。

两份流程均不设计复用先前 PR 或发布就绪后返工的业务分支，提示词不注入先前 PR 参数。对本次发布已产生的 PR 进行身份核验、查询和未知发布原操作对账仍属必要事实处理，不因删除上述业务分支而移除。
