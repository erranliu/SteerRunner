# Spec：L3 执行稳定性验收

> 本文固定首批远端稳定性的六场景/十二 case 范围，全部继续保留在 L3。新增本机流程后，
> 当前完整清单与计数以[测试清单](../test-catalog.md)为准；本文的历史 36/36 不代表当前全集资格。

日期：2026-10-15。状态：已实施；2026-10-16 同一构建完整三轮真机资格验收通过（36/36），无排除。结果及失败历史见[专属验收](../acceptance/l3-execution-stability.md)。

配套 [Plan](l3-execution-stability.plan.md)。生产行为依据 [Runner Spec](steerrunner.spec.md) §3、§5.3、§8–9；现有入口与 smoke 契约见[测试说明](../testing.md)。本文规定新增测试的覆盖和判定，不增加生产工作流、自动恢复或自动合并能力。

## 1. 目标与范围

首批交付为现有 `orca-remote.smoke`、五个新增 P0 场景及统一故障取证能力。全部在 Windows/amd64 调用端、已配对的真实 Orca environment、真实 Codex 和 `erranliu/SteerlineTest` 上执行。模型、Git 操作、PR 和原生会话均真实；允许测试设施制造通信或进程故障，不能伪造原生成功、状态、回执或产物。

本批验证五条性质：已接受任务不随调用方退出而丢失；连接恢复不重复输入；服务换代遵守显式继续门槛；停止授权撤销持久有效；发布结果未知不重复发布。每条性质都必须有动作和资源身份的正、反证，不能只检查最终文件。

不包含多轮反馈压力、多个 Run 并发隔离、长时间资源增长、其他模型/平台矩阵、SteerLine 集成、安装或发布。现有 smoke 的一次反馈、真实合并及收尾契约保留。新增成功恢复场景验证首次交付并合入专属 base，不额外重复反馈轮。

## 2. 固定场景与必跑变体

场景注册到 `tests/catalog.json`。一个场景可有多个必跑 case，每个 case 和每次重复都创建独立现场、Run、工作区、分支与专属 base；不在同一 Run 叠加多次独立故障后声称分别覆盖。首次支持的固定集合如下。

| 场景 ID | Case ID | 预期业务结果 | 核心验收 |
| --- | --- | --- | --- |
| `orca-remote.smoke` | `default` | merged | 保留当前完整 smoke，包括一次原会话反馈 |
| `orca-remote.caller-exit` | `accepted-response-lost` | merged | 接受后结束调用方，原请求找回且执行继续 |
| `orca-remote.connection-reconnect` | `active-disconnect` | merged | 服务不换代，真实断连后重接原资源并继续 |
| `orca-remote.service-restart` | `graceful-active`、`kill-active`、`graceful-boundary`、`kill-boundary` | merged | 正常停服与异常终止各覆盖活动回合及阶段边界；恢复前禁止新输入 |
| `orca-remote.stop-revocation` | `active`、`boundary` | stopped | 准确停止原执行；授权撤销后不产生新输入 |
| `orca-remote.stop-revocation` | `unreachable` | revoked-unverified | 停止时不可达，正确保留未知、授权撤销和恢复门槛 |
| `orca-remote.publication-unknown` | `completion-gap`、`query-unavailable` | merged | PR 已存在但 Runner 尚无完整完成证据；对账原 PR，零重复发布 |

完整 L3 每轮为六个场景、十二个 case，含十一个新增故障 case。`-Scenario` 仍按精确场景 ID 选择，选择场景即执行其全部 case，不在本批新增任意 case 筛选。漏 case、零执行、未命中故障和意外 skip 均失败。

`-Repeat` 默认为 1，取值 1–10，仅控制选中 live case 的独立重复；L1/Controlled 在该批 live 前完整执行一次。首批资格验收要求相同源码、EXE、工具、模型/effort、原生权限与注入配置下 `-Repeat 3`，即完整 L3 三十六次 case 执行。每次失败保留原记录，不用补跑覆盖。改变配置后作为新批次，不能拼成连续通过。

## 3. 观察、身份与故障设施边界

业务操作一律使用公开 Runner CLI，状态以已提交的 inspect/命令回执/events 为准。不写 SQLite、私有 checkpoint 或 adapter 状态来安排时序。原生只读查询用于独立核验和注入定位，不能替 Runner 保存业务结果、回复或执行下一阶段。

全程绑定 fixture/case/repeat、request_id/command_id、Run、operation、服务实例、Attempt、原生 session/turn，以及 Orca runtime/worktree/terminal/incarnation/pane/provider session。恢复允许产品契约认可的新 Attempt，但必须证明仍为原会话、原工作区和原分支；旧/新 Attempt 对应关系保留。普通重连不得无故替换 Attempt。最终 PR 绑定 repository/base/head 和原生 final 来源。

设施必须满足：

1. **事实屏障。** 先取得接受回执、原生输入已接受且开始、checker 已进入、发布器已确认真实 PR 等可验证事实，再执行注入。阶段边界用测试 checker 的有界门等待、原回合完成但 Runner 尚未观察等手段定位，不能以固定 sleep 或屏幕上的“idle”代替。
2. **真实中断。** Orca CLI 通信与 Runner 直接使用的原生状态订阅/查询是不同通路。完整断连须覆盖两者并证明原有连接已失效、新连接不能成功。只让 CLI 包装器返回错误不能算完整断连；单纯丢状态订阅而查询仍可用只可记为局部诊断。
3. **故障范围。** 网络、进程、控制门均限本轮独立资源。不得关闭整机网络、停止共享 Orca runtime、终止共享 CLI 安装或其他 Run。使用专属 CLI 安装/副本时保留必要运行文件，版本及哈希固定，认证仍由原生自身解析，不复制账号凭据。
4. **无业务代办。** 测试控制器可释放测试门、断开通信、结束精确进程和只读核验；不能代替模型修改/提交业务文件、push、创建 PR 或拼接 final。测试门与审计文件位于独立控制目录，不进入业务 diff；脚本版本、摘要和控制计划冻结。
5. **有界与可收尾。** 每次外部动作前落盘原身份和注入意图，动作后记录确认事实；丢回执不更换身份重做。控制门到期报错，不能默认为释放成功。测试设施异常或未命中注入点均为失败。

注入设施支持的能力及作用路径须在启动真实模型前验证。权限不足、无法隔离共享进程、不能切断状态查询或不能取得原生动作证据时，所选场景失败，不降级为 smoke 或跳过。准备失败后不继续创建该 case 的业务 Run。

## 4. 逐场景行为

### L3-S01：调用方退出

由测试专用调用方启动真实 submit CLI，保存原信封、正文摘要和 request_id；允许抑制其响应向上交付。通过另一个 CLI 的 `inspect --request-id` 证明该请求已接受，再结束该调用方及其所属 submit 进程；不得结束 Runner 服务。记录进程身份和结束事实，避免快速 CLI 已退出时假称测试完成。

服务实例保持不变。以原 request_id 找回唯一 Run，使用原 ID/正文重试 submit 返回原回执，不新建原生输入。原执行自然推进至 pr_ready，按原 smoke 的身份/内容检查及精确 head 合并规则核验。不能通过重新 submit 一个新 ID 挽救故障。

### L3-S02：连接中断与重连

在原实施回合已开始、checker 控制门已进入时切断本轮两条通信通路。独立诊断链路证明远端原执行仍存在；本地证明原连接断开、查询失败且服务实例未换代。断连保持至少一次完整失败观察和一次重新连接尝试，不能只记录注入命令成功。

恢复通信后释放原 checker 门，Runner 可以自动重接原观察并继续既定工作流。不得新增 resume_required，不要求额外 resume，也不重发原回合输入；合法的新阶段输入与重发分别计数。最终完成原 PR 并合入。

### L3-S03：服务换代与显式恢复

四个 case 分别采用公开 `service stop` 或核验身份后的进程终止。`active` 点位为原实施回合仍在 checker 门等待；`boundary` 点位为实施原生完成但完成证据尚未交付 Runner，下一阶段尚未发出。分别独立执行，不交叉叠加。

先确认旧服务进程已结束和旧写者失效，再以同 EXE/state-dir 启动。必须产生新的服务实例，恢复同一 Run 并建立持久 resume_required。正常停服不等于远端执行停止；离线期间原执行和完成事实照实记录。

恢复后先释放/恢复原观察链路，使原执行可完成并只读保存原结果；显式 resume 前，所有未发送的步骤、prompt、答案和旧授权均不得投递。观察窗至少覆盖两次真实成功查询和两次 Runner 对账推进，且不少于 10 秒；无推进证据不能以等待足够久替代。

driver 随后读取最新 revision 和恢复资格，以新 request_id 发一次明确 resume；该操作属于场景规定的自动测试输入，证据明确记为 driver 授权，不描述为系统自动恢复。原会话和原资源可核实时继续原工作流，最终合入原 PR。正向恢复 case 中身份不明、旧写者未结束、不能 resume 或换会话均失败，不能临时改成“正确阻断”通过。

### L3-S04：执行中停止与持久撤销

`active` 在原实施回合等待时 stop；`boundary` 在原回合完成事实尚未交付、下一阶段尚未发送时 stop，然后交付迟到事实。请求使用当前 expected_revision，核验原命令接受与 `new_inputs_allowed=false` 已提交，再检查原生停止。

已在撤销前发送的操作单独登记，不倒算成撤销后的违规输入。撤销后不得发送实施/报告/发布/答案等任何新业务输入，迟到完成事实只能保存。核验实际原生资源停止后才允许 stopped；两个正向 case 要求原生停止确认，且不要求创建或合入 PR。

`unreachable` 在活动回合先切断两条通信通路再 stop。必须先持久撤销授权；原生停止未核实则保留 unknown/reconciling，不得报 stopped。保持故障跨一次服务重启，验证撤销仍有效，未授权的后继输入为零；反馈及旧 revision 写请求不能绕过门槛。该 case 不发 resume。

恢复通信后仅对账停止原资源，必要的精确资源清理由 driver 单独记账；独立清理不能冒充 Runner stop 成功。预期 revoked-unverified 指故障窗口的业务事实，最终清理仍须确认原资源已结束。现场真实返回 unsupported 时保留能力缺口，属于本批目标能力不满足而失败；unsupported 的状态表达规则另由受控测试核验。

### L3-S05：发布完成证据缺口

使用本轮冻结的真实发布器，在 push/创建或复用 PR 后查询并保存实际 repository/base/head/URL；发布器通过控制门等待，不立即返回结果。独立 driver 确认目标分支确实只有一个 PR 后，切断 Runner 的两条 Orca 通信通路，再释放发布器；独立只读查询证明原发布回合完成而 Runner 尚未取得匹配的完整 final。

必须证明丢失的是 Runner 所需的完成证据，不是仅隐藏 driver 控制台上的一行 URL。故障期间不得按超时宣布成功或另发发布回合；之后只读取得原 final 和原 PR 事实，不得再次执行发布脚本或 `gh pr create`。统计本轮发布输入、发布脚本、创建 PR 的实际调用及真实 PR 总数，预期均为一次；查询可重复，补报不得再次发布。

`completion-gap` 恢复原观察后核验原 final、同一 PR 和真实 head，推进 pr_ready 并合入。`query-unavailable` 在恢复原观察后继续使 Runner 的 PR 查询不可用：保存明确查询错误/对账缺口，不能使用旧快照冒充最新确认，不能进入未经核验的 pr_ready；恢复查询后才完成同一 PR 的核验与合入。允许缺口期间保持运行/对账状态，精确状态取决于缺少的证据，不强迫一个错误的固定状态名。

本批覆盖真实发布已发生后的完成证据和查询缺口；不声称覆盖平台已创建 PR 而创建方自身永久丢失响应、原生 final 永久不可恢复等所有不确定性。

## 5. 结果、证据和通过判定

测试 outcome、业务 outcome、清理 outcome 分开记录。预期停止或明确撤销未知可以是测试通过，但不能写作业务交付完成或停止确认。预期结果由冻结的 case 契约决定，driver 不得在故障后根据实际表现修改。

每个 case 保留以下逻辑证据，实际 JSON 字段由 Plan 对应实现固定：

| 记录 | 必须包含 |
| --- | --- |
| 冻结 manifest/source identity | 场景/case/repeat、请求与材料摘要、源码/EXE/driver/helper 摘要、工具版本、环境/runtime、模型及权限配置、预期结果与期限 |
| 故障 journal | 意图、屏障事实、目标完整身份、开始/命中/恢复/失败时间、真实生效证据、恢复确认；同宿主次序用单调时长或序号 |
| 操作与原生调用 journal | 意图/回执关联、实际 native send/launch/close、业务与控制/诊断调用分类、发布器及 PR 创建调用；不能只数 CLI 查询次数 |
| 状态与事件 | 注入前后、换代后、resume 前后、stop 回执后及迟到事实后的 inspect 快照、命令回执、事件页和原生来源 |
| 产物/PR | 独立 fetch 的 Git objects、真实 PR 列表、repository/base/head、checker、合并 commit；非交付 case 核验无意外发布 |
| 结果与清理 | 命中数、全部断言、业务结果、Runner 停止状态、driver 清理事实、服务退出、控制门/网络规则/辅助终端处理及失败原因 |

动作证据来自真实通信边界的透明调用审计、原生回执/查询和发布器审计的相互校验；不得把“模型说只执行一次”当作调用计数。计数缺失或来源不完整失败。不得持久化认证 token、配对秘密或完整环境变量。

测试通过同时要求：所有必跑断言通过、注入命中、无身份替换/重复副作用、预期业务结果成立、原生 owned 活动结束、服务退出、故障设施撤除并确认。PR/分支/工作区和证据按现有规则保留，不删除历史失败。未知/超时只在指定窗口作为预期中间事实；最终无法对账或无法清理均失败。

成功交付 case 复用原 `CheckPR`、final 来源、真实 Git 内容及精确 head 合并校验，不放宽原 smoke。非交付 case 的清理使用专用判定，不要求 merge_commit，也不伪造 run_stopped；清理完成不覆盖业务原本未知/失败的事实。

批次 summary 明列 requested/selected scenario、展开 case、重复次数、计划/实际执行数、每次原始结果、首次通过率和各阶段耗时。完整套件连续三轮全通过才可声明本版本完成首批 L3 稳定性验收；子集只能声明该子集通过。统计不把旧版本、手动介入或诊断补跑混入。

## 6. 期限与失败处理

复用现有单场景上限 60 分钟的约束，每个 case 独立计时。默认每 case 30 分钟；包含重启或发布缺口的 case 可冻结为 45 分钟，禁止运行中延期。原生执行的既有等待预算保持产品语义，不因测试重试重置。

测试控制门默认上限 600 秒；单次注入/恢复确认各 60 秒；通信故障窗口默认 60 秒，跨重启的 unreachable case 冻结为 240 秒；重启与恢复资格核验各 120 秒；最终收尾预算 120 秒。重启 case 的门预算覆盖换代、恢复观察、授权前观察窗及显式继续，不允许门先超时却把源失败算作恢复成功。这些预算包含在 case 总期限内，driver 须预留收尾时间，在 harness 硬超时前进入清理。窗口不能命中所需事实即失败，不能延长等待直到偶然命中。

进程异常退出或硬超时导致缺结果时，批次失败并保留原 state-dir/request/Run/资源身份。收尾工具只能对账原身份和撤除本次设施，记录为失败后的处理；修复后创建新现场，禁止复用已执行 manifest 或重写旧失败结果。
