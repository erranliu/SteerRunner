# Runner 提示词收敛与输入字节预算 Spec

日期：2026-10-28。当前修订：取消调用方及总正文上限，仅保留 Runner 1000B；历史验收仍绑定当时版本。状态：已按用户授权实施预算与提示词收敛，见 [Plan](workflow-input-budget.plan.md) 和[验收](../acceptance/workflow-input-budget.md)；真实后续输入已接受，但 Runner 完成确认未通过，不宣称投递缺陷已修复。兼容性标准为保留现有功能及其有效执行路径，接受正常提示词精简的潜在影响；不要求所有旧长输入原样继续接受。范围仅为 Runner 文本输入契约及预算；不部署、不恢复原 Run，验收限本稿最小范围。

## 1 目标与边界

Runner 只向模型提供完成当前步骤必需的目标、材料引用、动作边界和结果要求。执行控制、完整来源核验、内部验证台账和平台配置由现有程序负责。收口分散追加入口，先减少输入负担，再用最终字节检查确保超限输入不会投递。

本期复用内置 workflow、现有请求和投递路径、原 Run 记录与生命周期。不引入新框架、DSL、模板解释器、插件注册机制、第二账本或额外运行时协议文件；不生成或依赖新的 runtime.md、材料清单文件、目标文件或证据读取工具。不修改 SteerLine、业务目标、Spec/Plan、固定测试安排、项目约束或发布目标。

不以删减必要约束、截断、自动摘要、增加模型轮次或拆分输入解决超限。提示词精简不等于修复后续发布投递缺陷，两者分别验收。

## 2 功能保留与允许的精简影响

正常精简导致的模型措辞、回复组织、工具选择或结果获取方式变化可以接受，不要求相同模型逐字返回旧回复或重复旧工具序列。业务目标、固定测试安排、完成条件、结果字段、权限、身份/来源核验、幂等与生命周期要求保持，不得以“模型行为有波动”为由放松这些要求。

硬性能力丢失指删除或关闭已有功能/后端/操作、破坏恢复或文件通道、移除必要结果获取路径，或使某项功能仅剩名称而无预算内可用路径。本期禁止这些退化；不能通过关闭 parser、删除 capability 或禁用整个 workflow 来满足预算。

当前输入预算仅约束 Runner 生成文字 R≤1000B。调用方正文、覆盖、回答、反馈、inline 材料和 schema 不设正文预算，总量也不设 3000B 上限；C、R、T 继续准确计量并冻结。既有 API 请求、材料配置、实际传输封装和命令行容量保护保持，取消正文预算不承诺任意大小可传输。历史 10552B 实施输入或 3767B 发布输入不因旧 2000/3000B 额度而拒绝，但仍须满足 Runner 预算、来源和传输条件。

| 现有能力与风险 | 本期兼容要求 |
| --- | --- |
| development、development-audited、conversation、generate 及已公布的适配器/目标/Agent 组合 | 保持原功能、操作和原生身份/模型选择语义；不能通过删除 capability、关闭 parser、拒绝整个 workflow 或取消某个后端来取得预算验收通过。预算内的原合法输入必须有等价可用路径 |
| 冻结 State、PromptBodies 与旧 Run 恢复 | 新默认文字只用于相应的新输入定义，不覆盖旧冻结正文。兼容检查不能因新默认 ResultInstruction 等文字变化就把旧 Run 判为 unsupported，也不能笼统忽略整个 State 以放松状态边/模型角色/契约核验。旧超限输入只拒绝该次新派发，不取消整项恢复、观察或结算能力 |
| prompt_overrides | 保持既有覆盖范围：report 的独立格式要求保留；审计 execute 原本位于可覆盖正文中的格式不能不经契约变更就升格为不可覆盖后缀。程序结果核验及原 parse/report 获取规则保持 |
| 可选独立 parser 与一次 report | 保持程序提取优先和原获取策略。parser 未派发且完整证据预算不合格时，可保留原本已授权的一次 report 路径；不能直接令整条结果获取失效。report 只整理原会话已有上下文，不重审、不新增报告次数或放宽来源校验 |
| conversation/generate 的 inline 材料、自包含 output_schema、固定仓库调查及多文档结果 | 保留各功能在新预算内的可用路径，沿用输出字段、目录/快照、只读权限及程序 schema 校验。调用方材料/schema 不受正文预算限制，Runner 包装仍校验，不关闭整个功能；不擅自把 inline 改成文件引用或声称 SnapshotPath 已是正式模型材料引用 |
| progress/result、问答、stop/resume、接管与未知结果对账 | 只减少无关指令，保留原变量/文件/字节、问题和会话身份、封存/观察时机、持久授权及资源结算；预算拒绝不清空原结果、不吞掉问题或反馈、不触发隐式重做 |
| 原始请求、模型输出、材料快照和文件通道容量 | 1000B 仅限制实际模型输入中的 Runner 生成文字，不限制整个 submit/inspect/history 对象、原生 final、结果列表或文件字节；不把 progress/result 65536B、generate 结果 1MiB 等现有上限改成输入预算 |
| 原生命令头、模型桥与环境规则 | 先缩短指令，不改原标识/模型/权限协议。若固定必要文字或包装自身已超限，该组合属于未解决问题，不能只登记“超限拒绝”就算保留现有能力 |

本期允许复用原有 report 后备，是原获取策略选择，不是将同一长输入分片投递。预算不合格的 parser 候选不得发送，也不创建假的 parser 尝试/接受事实。若 parser 已尝试、结果未知或资源未结算，仍须先对账，不得切换后备；report 自身也须满足 Runner 预算，预算不足不能再生报告轮。

无论 final 多长，先沿原程序提取和 schema/业务校验处理，不能先把输入预算套到 final 上阻断已可程序取得的结果。删去完整内部对象时，仍须向模型保留完成当前步骤所需的失败、未知、业务约束及发布事实；源记录中存在该信息不能代替向无上下文的解析器提供材料。

删除 progress/result 的无关提示副本不删除环境变量、不改变文件准备/观察/封存、不改变原工具写入权限，也不新增所谓“生产者授权”状态；仅按现有步骤语义决定是否附带 Runner 引导。调用方内容及既有文件契约保持，不能把提示词清单解释为扩大或撤销文件通道能力。

以下容量影响须明确记录，但不要求为保留旧输入大小而扩展本期范围：

- 现 parser 可接收至多 65536B 原 final，默认 package 输入上限为 131072B；完整 final 进入新模型输入时仍受 Runner 1000B 限制。独立 parser 必须保留预算内实际可用的解析路径；长证据超限可沿原一次 report 后备，但不能把 report 成功冒充独立长证据解析容量未变。
- 内容流程的调用方指令、inline 材料和内嵌 schema 不再受 2000B 预算限制；Runner 包装仍须在 1000B 内，原传输和材料配置限制保持。不为保留旧容量新增协议文件/读取工具或假设另一条已验证交付通道。
- 旧超限冻结输入不重写、不继续发送；拒绝该次输入时保留其材料、请求关联和原结果，观察、停止、查询、结算及其他预算内的合法操作仍可用。

功能保留的通过条件是每项已有能力在新契约内仍有包含真实必要字段和正常身份长度的有效执行路径，不是只证明某个空消息可发送。若某个能力的必要固定指令、包装或最小有效业务输入自身就超预算，必须继续整改并列为未通过，不能以“正确拒绝”掩盖整项功能失效。一般超预算输入拒绝及正常精简造成的模型表现变化不再要求证明全旧容量或完全相同行为。

## 3 提示词删除保留和精简清单

下表的“删除”是删除模型输入中的副本，程序记录、必要校验和原证据继续保留。“精简”必须保留列明语义，不改变业务要求或来源核验强度。

| 当前内容 | 整改要求 | 必须保留的语义与取舍 |
| --- | --- | --- |
| 完整 implementation_result、audit_result 及其 Attempts、Fields 等台账 | 删除完整对象投喂，仅保留当前步骤必需的事实及程序关联引用 | 完整前置资格及来源在程序侧核验；结果 ID 不能代替模型实际需要的材料，也不能假定模型可凭 ID 读取内部记录 |
| publication_policy 整体及 provider 内部配置 | 删除整体投喂 | 发布所需目标仍必须准确提供；查询命令、认证配置等不进入正文 |
| 报告中的完整 workspace、重复材料 JSON、冗余来源字段 | 删除无关副本 | 保留原业务源关联、必要成功/失败/未知状态；完整绑定继续持久保存 |
| Spec、Plan、Reference 路径 | 保留既有正式材料引用，由最终字节预算约束合计大小 | 沿用现有来源和调用方负责开发材料可用性的边界；不新增 Runner 文件验证，不改成未经支持的短别名或新清单 |
| 发布 repository、remote、base 等必要目标 | 合并重复项，使用有界字段 | 不能省略或改写目标；长值超限即拒绝，不用新目标文件兜底 |
| 实施、审计、发布基础正文 | 精简为当前步骤动作，删除重复背景和流程说明 | 实施及必要验证、审计修复与提交、发布范围等原要求保持 |
| 统一结果格式及审计字段说明 | 去重并精简，按现有覆盖范围归入正文或固定片段 | 程序需要的 outcome、summary、question/blocker、PR URL，审计数量与列表、证据、遗留问题及完成条件保持；不借此收紧显式覆盖的既有输出方式，未知不得推断为零或成功 |
| 提交要求 | 合并进需要提交的执行步骤，避免重复 | 仅精确暂存任务路径、检查暂存差异、串行提交并立即保留 commit 自身退出码；失败或未知不重试 |
| 成功行引导 | 缩短引导句，保留当前完成标记原文 | 继续逐字识别当前阶段原 final；不放宽匹配，不以标记代替 Git/provider 核验 |
| progress 写入说明 | 仅在启用且声明为生产者的实施/审计执行步骤保留短说明 | 沿既有环境变量；原字节、大小上限、锁内读合并及同目录原子替换语义保持；发布、report、parse、只读步骤不附写入引导 |
| result 写入说明 | 与 progress 区分，仅给声明的执行生产者；删除无关阶段副本 | 独立文件、协调写入和原子替换；全执行结束且生产者停止后一次封存，不能由单轮结束或 pr_ready 触发；不解释业务成功 |

| Git 2.55 提交告警处理 | 仅在涉及提交的步骤保留精确短规则 | 仅原已知 AUTO_MERGE/packed-refs.lock 清理告警，在捕获退出码为零、核实 HEAD 前进、父提交/变更路径正确、工作区干净且无待合并/拣选/回退状态后可继续；其他失败或未知仍阻断，不重复提交或修复拒绝的清理 |
| 只读会话与环境检查 developerInstructions | 与适用步骤正文去重，使用固定短说明 | 只读范围及禁止写入/提交/发布；环境检查限定工具、绑定 nonce/动作顺序、失败即停、不重做未知动作 |
| 反馈包装及原生问答 | 精简标签，回答正文不改写；全部入口纳入预算 | 回答只绑定原问题/原轮；覆盖正文和反馈仍全部计入调用方，但不设正文预算，不重复注入整份状态或问题上下文 |
| 独立解析器的边界、审计格式和完整 final | 精简重复说明；完整内嵌证据全部计量 | 只整理既有结果、无工具和副作用、不编造未知事实；保留原生结构格式及程序校验。超限只拒绝该候选；原已授权 report 的选择和预算按第 2 节，不新增读取能力或模型轮次 |
| conversation/generate 包装、材料及 schema 说明 | 缩短标签，去重只读和固定版本说明 | inline 材料、调用方 schema 拼入正文时照常计量；固定快照、来源引用及返回格式要求保持 |
| 命令、摘要和模型切换标识 | 保留现有编码和身份核验，将实际标识计入预算 | 本期不重设计模型桥或短标识协议；必要包装造成超限时拒绝该次输入，并列明支持限制，不凭缩短正文宣称所有组合达标 |
| Runner 编写的工具自然语言说明 | 保留必要用法，固定短化并公开登记 | 原结构化参数和程序校验保持；不能把普通指令藏进工具/schema 描述字段逃避计量 |
| 无生产调用的旧反馈/历史输入包装入口 | 删除废弃入口，或明确不可派发 | 不保留可绕过公共输入检查的备用入口 |

Runner 主动构造的输入文字，包括错误/异常指令、progress/result 说明、初始化与会话级说明，均须在公开输入契约中显式声明。阶段语义仍归内置 workflow；通用初始化和工具用法等由原 owner 定义固定文本/片段并在公开契约中引用，不把它们复制进每个 workflow 或让适配器依赖 workflow。文档与执行引用相同定义，不建设通用提示词注册/解释框架。

本期不把模型约束变成新的权限隔离。report 只报告的既有提示词政策、原生权限与事后核验仍分别表达；不因删除写入引导就宣称原生只读已实现。

prompt_overrides 只替换原契约声明的正文，不能为了统一模板而改变现有覆盖边界。材料与来源插槽、报告结果格式、适用的提交/完成要求等既有固定片段仍保留并逐项公开；审计 execute 的默认 JSON 说明原在可覆盖正文内，显式覆盖仍可依赖现有程序提取/可选 parser/一次 report 获取结果，不强加新的 JSON-only 后缀。改变覆盖范围须作为明确的公开契约变更另行处理，不能静默作用于旧 Run。覆盖正文按调用方计量，默认正文按 Runner 计量。

## 4 唯一输入出口

唯一出口指唯一的预算判定和冻结规则，不要求所有输入经过同一个 application 函数。workflow/application 继续装配阶段和业务文字，parser owner 继续装配解析输入，适配器继续编译原生标识、终端换行和会话参数；各入口在文字最终确定处复用同一小型纯计量/校验函数，沿原记录与持久意图派发。

阶段执行、report、独立 parser、初始化、developerInstructions、环境检查、内容输入及同步/异步回答均须覆盖；普通工具执行结果、文件读取结果和 SDK 自带基础上下文不纳入这次新增文字预算。不能为此新增输入调度器、回调流水线、统一原生客户端，或将业务编排搬入适配器。

固定顺序如下：

1. 各原 owner 从公开定义选择本次输入的正文、必要片段和数据；未声明的指令/包装不得派发。
2. 在各自现有装配位置完成插槽渲染、正文 JSON 转义、原生标识及必要换行处理，再进入共同检查。现有 CRLF/LF、尾换行行为须明确声明；不得为省预算额外删除调用方空白或改写内容。
3. 按最终实际文字确定全部字节归属，检查 Runner 1000B 预算并记录 C/R/T。
4. 在已有输入记录/意图中保留最终文字，补充摘要、分项字节数及来源；只绑定发送前已存在的身份。
5. 对实际传输封装和最终 Windows 命令行另做保护，核对待发送文字与冻结记录一致后投递。

阶段正文已冻结不代表最终输入已检查。例如 Orca 在既有准备输入阶段生成命令头后，应对该最终文字调用共同检查，并将结果保留在原操作记录；不能要求 application 为此调用 adapter 的渲染逻辑，或增加跨层回调。共同检查只接收已装配的文字及来源片段，不解释业务步骤或决定下一动作。

适配器可以在共同检查前生成既有原生包装，但检查/冻结后只能编码、分帧及投递，不能再改模型可见文字。输入标识如需命令 ID，必须在冻结前取得；新原生 Turn ID 在回执后沿原记录绑定，不预造身份。物理终端控制字节单独计入封装，不计作模型正文。

计量单位是一次现有模型输入投递操作中实际发送的全部新增文字字段。同一次 thread/start 的 developerInstructions 和 Runner 工具说明合并计量；后续 turn/start、turn/steer 或原生回答各自计量，不创造跨请求的“逻辑输入”事务。字段按实际顺序和定位记录，不虚构字段间分隔符；已存在于会话的指令和历史不重复累计。

现有初始化与业务输入继续按原生命周期分别发送，不能新拆请求/轮次或把超限任务改放 session 字段绕过预算。文本归属由来源确定，不因 API 字段名、消息角色或投递操作改变。

恢复尚未发送的输入使用原冻结内容，不再追加 progress/result、反馈或当前默认值。旧输入若能只根据原冻结数据可靠补算归属，可在不改原文字且满足既有恢复资格时继续；无法可靠计量则拒绝该次新派发。已投递输入保留原接受/结果事实，未知只对账，不重发或追认成功。输入预算不能阻止原观察、停止、资源结算或记录读取，也不要求全局状态迁移。

## 5 字节预算和上限目标

令 C 为调用方最终文字字节，R 为 Runner 最终文字字节，T=C+R。统一使用 UTF-8 实际字节，仅 R 设正文硬上限：

| 条件 | 硬上限 |
| --- | ---: |
| C | 无正文预算 |
| R | 1000B |
| T | 无正文预算 |

调用方再短也不能使 Runner 超过 1000B；取消总量额度，避免间接限制调用方。公开 `utf8_bytes.caller` 和 `total` 为 `null`，明确表示无正文预算；`runner` 为 1000。字符数、Unicode 标量数、UTF-16 长度或 API JSON 封装大小均不能替代正文计量。

| 归属 | 内容 |
| --- | --- |
| 调用方 | 正文、显式覆盖、回答、反馈，包含原文内部换行和标点；直接内嵌的调用方材料和 schema 内容，以及为保留这些内容产生的正文转义 |
| Runner | 默认正文、workflow 指令、选取/派生的事实、材料引用、目标、状态、自然语言工具说明，以及 Runner 新增的标签、分隔符、换行和 JSON 外壳 |

按来源片段计量，不逐字符另定责任：调用方原文内部换行归调用方；Runner 在片段之间新增的换行归 Runner。适配器必要的 CRLF/LF 处理在计量前完成，处理后的原文仍保留原片段归属。调用方直接提交的 JSON 内部标点属于调用方，Runner 为包装该内容另加的 JSON 外壳属于 Runner；同一实际字节只能归属一次，C+R 必须等于 T。

转义后的两个字节 `\n` 若只是正文 JSON 字符串内容，不等同于实际 LF。文件和工具读取结果不计本次文字预算；若 Runner 再选取其内容拼入新输入，则计入 Runner；调用方明确提交的 inline 材料仍计调用方。原生问答中的人工回答不能伪装成免费工具结果。

正文计量对象是模型实际收到的文字。JSON 作为正文内容时，其引号、反斜杠及转义文字照常计入；仅为外层 RPC 序列化产生的转义计入传输封装，不重复计作正文。

动态插槽只允许当前步骤明确列出的必要字段，不能原样序列化任意内部对象。复用既有字段/枚举/条数约束，Runner 生成片段的组合大小由最终 R 检查兜底，C/T 只计量；不新增逐字段配额配置体系或字段预算分配器。材料引用保持现有相对路径及可访问性责任，不能因本期整改扩建材料复制/验证服务；不支持的引用和造成整体超限的值明确拒绝。

| Runner 设计目标 | 目标值 |
| --- | ---: |
| 初始化、简单反馈包装 | 不超过 256B |
| 常规实施、发布及普通内容输入 | 不超过 512B |
| 审计、结构化报告和独立解析等复杂输入 | 不超过 768B |
| 任一步骤最终拒绝线 | 超过 1000B 必须拒绝 |

目标包括适用的默认正文、动态事实、会话说明、标识和换行，是本期压缩方向，不是新的运行拒绝线。超过目标但不超过硬上限的输入可投递，验收报告必须列出实际值、主要来源和取舍，不得宣称目标已达成；不承诺任意合法长路径、任意材料数量或任意 final 都可接收。

传输保护独立设置在原编码/发送入口：检查 Runner 实际构造的输入封装大小，以及实际走 Windows 命令行的完整转义命令行长度。分别依据所用客户端/终端/进程 API 的有效限制确定并记录阈值；不使用未经验证的统一 64KiB/30000 阈值，不放宽已有更严保护。验收给出所测原生路径的阈值依据和边界，Runner 正文预算不能代替它们；不为此扩展不承载模型输入的 RPC。第三方内部不可观测的再次封装注明范围，不能以重建估算冒充实测，也不扩建 SDK 网络追踪设施。

原生工具参数/schema 的结构本身沿原结构化协议和封装限制处理，正文中的副本照常计量；其中 Runner 编写的自然语言指令始终计入 Runner，不能藏进 description 字段豁免。

## 6 超限冻结和数据保护

任何最终候选预算超限都在该次输入投递前明确拒绝，诊断至少包含 C、R、T、Runner 上限、调用方/总量无正文额度及片段来源。不能只报“字符太长”。不要求准入时预演整个 Run 或预测未来阶段事实；后继阶段在自身文字确定后检查，不重做已完成上游步骤。

超限候选不得投递，不粘贴、不提交、不增加格式修正/补发轮次，不把超限状态标记成模型已接受或业务成功；已有获取策略的后备选择仅按第 2 节，不得借机新增轮次、分片或摘要。正文合格但传输超限时报告独立传输错误，不能修改正文重试。预算拒绝保留原提交、材料、final、问题及待处理命令的关联，给出可查询的明确拒绝结果，不能吞掉请求或把原业务结果改成失败。

冻结事实复用已有输入文字与原私有 Run/operation 存储，只补充确实缺失的 SHA-256、C/R/T 和片段来源/归属/字节数；不重复保存多份完整正文，不新建输入权威或一套身份记录。新原生轮次身份在原回执路径补绑。投递端核对实际文字与冻结摘要，变化即拒绝发送；重启不重新生成另一份同名输入。源绑定、停止、权限和原生回执门槛保持。

凭据、认证状态及私有配置不因取证进入模型文字。冻结明文保持原私有访问与保留策略；公开诊断继续脱敏，仅给必要计数和来源名。脱敏显示不能替代实际发送文本的摘要证明。不另建 prompt 日志库或运行时协议文件。

## 7 验收标准

以下为本期验收要求。公共规则集中验证，既有入口只验证接线和特有包装；不把每个字节边界、Unicode 用例与全部 Agent/账号/模型/文件开关做笛卡尔积。实际通过、未达优化目标与真实验收缺口在验收报告分开记录。

| 验收项 | 必须证明的结果 |
| --- | --- |
| 公开契约与实际一致 | 阶段语义及通用初始化/会话/工具片段均在公开契约声明，文档与执行引用同一来源；不要求所有 owner 依赖同一个 workflow 对象 |
| 能力目录不收缩 | 对照改前/改后的现有 capabilities/schema，除明确新增的预算声明外，不删除已支持 workflow、适配器/目标/Agent 组合、操作或已有 parser 配置取值；不以缩减目录替代回归验证 |
| 唯一出口覆盖 | 各现有装配/投递入口复用同一计量与冻结规则；每种入口至少有一个接线用例及其必要包装检查，不要求统一装配函数或重建发送层 |
| 删除和保留清单 | 模型输入中没有完整内部结果/验证台账/provider 配置及无关材料副本；必要目标、来源、Git 特例、失败/未知和凭据保护语义保留 |
| 步骤隔离 | 在 workflow/application 现有渲染层覆盖 progress/result 四种开关组合及执行/发布/report/parse/只读分类；仅声明的执行生产者收到短写入说明，不要求每种原生后端重复四种组合 |
| 覆盖行为 | 默认正文与同文显式覆盖的归属正确；保留 report 固定格式与审计 execute 原可覆盖正文的差异；覆盖加反馈计入调用方且无正文额度，不无意新增 JSON-only 后缀 |
| 预算内功能回归 | 用既有受控用例覆盖普通实施/发布、审计零修复/有修复及后备、conversation message/reply/interrupt/close、generate 文本/JSON/schema 校验、环境检查和原生模型选择；保留业务完成条件、结果结构、必要步骤、权限/来源/幂等与生命周期，不要求模型措辞、工具选择或获取方式完全相同，不新增业务重做 |
| 边界值 | C=1999/2000/2001 及更长输入，T=2999/3000/3001 及更大总量不因 C/T 拒绝；R=999/1000 接受，R=1001 在短/长调用方两种情况下均拒绝 |
| 总量关系 | 始终 C+R=T，C/T 超过旧额度仍可通过；调用方再长也不能掩盖 Runner 超过 1000B |
| 编码与动态值 | 公共规则覆盖中文、emoji/非 BMP、组合 Unicode、LF/CRLF、尾换行、JSON 转义；明确区分调用方内部换行/JSON 与 Runner 新增包装。阶段用例再覆盖长路径、多引用、目标/异常文本及模型标识 |
| 超限无投递 | 每种入口至少一个超限接线用例，携带该候选的模型发送/粘贴/提交调用为零；不要求原只读查询、已完成上游输入或停止结算调用为零。所测原生路径另验证自身封装/命令行保护 |
| 冻结不变 | 冻结后改字节/归属被拒绝；恢复不重复追加。冻结文字与实际发送解码文字一致；仅在取得原生完整输入时比对原生文字，回执不足维持未知，不能用草稿字数代替 |
| 长结果与后备 | 长 final 可程序提取时不调用 parser/report；用正常长度身份及有效审计证据验证预算内独立 parser 可执行，不能仅测空 final。长证据超限保留原已授权一次 report，仍绑定同一原源；已尝试未知 parser 不切换后备。容量变化单列，不以保留功能名称代替实际可用路径 |
| 旧定义与记录 | 使用旧 State/PromptBodies/ResultInstruction、待发送输入、活动/未知操作及已结束记录验证兼容；新默认文字不能触发 unsupported 或改写旧输入，不放宽路由/权限/来源资格。旧超限输入的明确拒绝属于新预算结果，但不能让整个 Run 的观察、停止、读取或结算失效 |
| 非输入数据不受误限 | 保持大于 3000B 的原请求非模型字段、原 final、材料快照、progress/result 原字节及 generate 输出查询/保存能力；预算拒绝后仍能查询、停止和结算，无数据清空或静默丢失 |
| 设计目标报告 | 列出所测默认步骤、必要开关/覆盖及代表性包装的 Runner 字节数和构成，明确配置和目标未达项；未测组合不新增资格声明，已测合格输入不超过硬上限 |
| 兼容与范围 | 旧输入可可靠补算时不改字节；不可计量只阻止该次新派发，观察/停止/结算保持。不新增框架、DSL、运行时协议文件、读取工具、模型轮次或全局迁移；不扩展 Git/权限/材料服务 |

功能回归复用受影响模块的既有测试和受控原生/provider 边界，不要求重新运行完整原生资格矩阵或业务测试。某个已支持组合的必要固定文字、默认流程或最小有效业务输入仍超硬上限时，记录为未解决的硬性能力退化，不能仅凭“正确拒绝”宣称整改完成；一般长输入超限及正常精简潜在影响按第 2 节接受，不再将全旧容量兼容或模型行为完全相同作为验收门槛。

真实投递验收仅要求在原问题所用模型、账号、SDK 配置对应的全新独立现场，通过实际生产入口完成一条最小链路：初始化 → 首次短任务调用无副作用工具并完成 → 同一会话发布式短指令仅返回唯一标记，不创建 PR。已有初始化是否实际需要由原入口决定，不为适配该用例新增初始化轮。记录冻结文本/字节数、必要封装信息及两次业务输入的原生接受事实；预算拒绝测试使用发送边界受控验证，不要求真实投递超限内容。

“完成后立即发送”“明确就绪后发送”“增加首次工具输出”的单条件对照属于独立的投递故障定位，不作为字节预算整改的完整实验矩阵。若最小链路失败，保留原时间线、Orca 退出/超时/取消、粘贴/提交、草稿及公开回执，转入该定位工作；不得为取得通过记录无依据重跑。分别报告“预算/受控验证”和“真实投递”的结果，真实链路未通过时不能宣称原生投递验收完成。

未知结果不重发，不人工补 Enter，不放宽匹配。原已停止结算的 Run 和宿主不恢复、不重放；不运行 MagicPotion/Unity 或 SteerLine 业务测试。预算通过不作为历史发布投递根因已确定或缺陷已修复的证明。
