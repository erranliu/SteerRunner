## 1. 目标与范围

用户选定整体分析中的第 2、3、4 批：解除可选观测对执行的阻塞并建立快速验证入口；删除跨构建接管、退役权限兼容及资源丢失后的复杂恢复；收口 application 与 adapter 的职责。使用一份 Spec + Plan 管理，按“快速验证→观测解耦→恢复/兼容删除→有具体收益的职责收口”独立验收、独立交付；后续批次不作为前批交付前置。

目标是让固定任务在个人信任的本机或远端机器上执行，保留后台长任务、普通服务重启重连、Workflow 和 PR 交付，同时缩小后端改动的影响面及日常验证范围。接受执行资源丢失后由本人接管现场，不继续建设自动恢复所有异常的能力。不承诺本轮能显著压缩仍保留的原生取证、模型桥、控制通道或停止证明。

本稿只调整这些实施所必需的局部运行契约，不另立完整产品重定义项目。既有 full_access、宿主登录和独立 parser 简化已实施，不重复立项。

## 3. 观测与业务解耦（PES-01）

### 3.1 通道定位

`progress_file` 和 `result_file` 都是可选不透明字节通道，不作为 Runner 的业务准入或完成依据。本轮不增加 required/optional 策略、文件解释器或交付条件 DSL。调用方若依赖结果文件内容，应在消费端处理其缺失；不能由 Runner 猜测文件是否代表测试通过。

保持现有提交字段、固定路径、环境变量、base64/64 KiB 限额、原始字节、原子替换及查询格式。progress 独立版本和最后快照保留；result 仍仅在原执行结束资格成立时封存，成功 version=1、失败 version=0，封存后不刷新。`pr_ready` 本身仍不触发 result 封存。

### 3.2 一次有界准备

1. 在原工作区已绑定、首次业务输入之前，尽力准备启用的通道；两通道共享最多 4 秒的总准备窗口，包含查询、初始化、校验及读取。某一通道失败不取消另一通道的尝试，剩余预算耗尽按未确认处理，不另续预算。
2. 复用现有初始化尝试字段，在第一次准备前记录已经尝试；记录不能成功时不发文件写 RPC。该文件保存失败本身不另设业务门禁，正常业务自己的持久化失败仍按 PES-I01 禁止派发。
3. 只在原绑定固定路径 O_EXCL 创建；不覆盖已有文件。已尝试后，无论成功、失败、超时或响应丢失，都不再初始化。重启后可只读原文件，但不再等待初始字节一致才允许业务继续；agent 此时可能已写入进度。
4. 不在全局状态锁或业务 dispatch gate 内等待文件网络/磁盘 I/O。在短临界区核对原绑定/授权、记录尝试并登记初始化已越过派发界限；stop 已先提交则不越过该界限。跨过界限后锁外执行的有限文件动作视为在途动作，可有界结束；返回后复核原绑定和当前资格，只保存合法文件事实，不据此派发业务后继。
5. 到期或失败后仍推进原步骤。后续轮询不因 `Initialized=false` 重新进入准备或重新创建工作区/终端/helper；不在每个阶段再付出 4 秒等待。
6. 已合法设置的环境变量仍指向固定路径。初始化失败不生成假文件、假空快照或成功诊断；不使用本机同路径替代远端文件。

### 3.3 失败、恢复与收尾

progress 初始化或读取失败使用既有 `unavailable` 和有限诊断；保留已有快照。原绑定仍可读取时，后续采样可以恢复，即使初始化未确认；首次完整有效字节才形成快照，不补写种子。

result 的初始化异常仍表达为 pending 加诊断；到原结束采集点，能核实原绑定并读取稳定完整字节即可封存，不要求初始种子确认。不能取得字节时按原一次采集预算封存失败；不恢复资源、不等待文件出现、不重跑业务。没有原执行结束资格仍保持 pending。

观测准备、保存、采集及收尾失败都不得设置业务 blocked/reconciling/ResumeRequired、撤销授权或阻止 PR/stop 结算。保留 Record 当前快照合并和专用保存不增加业务 revision 的规则，不增加第二数据库或通用观察服务。既有费用采集独立 worker 及其远端日志 permit/lease 不属于本轮权限删除范围。

## 4. 恢复与升级收缩（PES-02）

### 4.1 升级约定及状态目录

普通服务重启保留重连；安装升级采用“原版本先排空，再启用新版本”的操作约定，不提供跨构建活动任务接管保证，也不支持在同一目录混合管理多构建活动 Run。不新增构建权限模型、逐 Run 构建摘要字段、按 EXE 差异分类的 worker/controls/停止分支或自动选择历史 EXE 的机制。实际 EXE SHA 仍可用于既有来源记录、实例绑定和精确资源身份核对，这些用途不用于决定某个 Run 是否有业务操作权限。

恢复/兼容删除批次使用 `steerrunner-state/v7`、SQLite user_version=7 和默认 `%LOCALAPPDATA%/SteerRunner-v7`，作为删除 v6 退役权限/恢复编码的一次性边界。此前独立交付的快速验证、观测批次继续使用当前 v6，不提前切换目录。P3 新版本拒绝 v6 及更旧目录，零 worker/owner/远端调用，不迁移、不删除、不将旧记录标记为停止。旧任务、查询和资源收尾由原版本完成；配置 skill 必须显示状态目录变化，不暗中改写用户显式 state-dir。

以后仅在实际持久格式或执行契约不兼容时更换格式/目录，不因 EXE 字节或路径变化就要求新目录。格式保持兼容且原版本已排空时，可继续使用原目录并查询其历史通用事实；保留当前必要解码，不维护历史私有 codec 的多版本矩阵。新版本不为了启动而把未结算记录改成已停止，也不把它们认领为新任务。

排空包括业务不再待输入/继续、原生资源已按现有范围结算、无未完成副作用或控制命令；不能只看 `pr_ready`。无法确认时保留原 EXE/state-dir，由原版本和用户处理；本轮不新增逐 Run 构建识别或自动排空系统。不按约定携带活动任务升级属于不支持的使用方式，不以“升级成功”推导这些任务已接管或停止。本轮文档不操作现有数据，不授权安装、排空或强杀用户任务。

### 4.2 普通重启重连保留的行为

服务退出仍只脱离观察，不默认停止后台 owner/Agent。原执行版本重新取得 writer 后，沿原 Run、操作、owner、session 和业务游标接回仍存在的执行，补收原回执/final，保持暂停、等待、stop 和里程碑。已授权且尚未形成外发意图的唯一业务后继可按现有事务规则继续；没有额外 EXE SHA 相等的 Run 准入判断。

保留独立 execution owner、原连接、Job/控制终端、创建执行器的原回执和必要 checkpoint；删除跨版本接管不等于删除后台执行。准备期间资源尚未创建且没有可能已发送的动作时，可以继续首次准备；一旦原动作可能发生，只读原回执对账，不重新 create/send。

### 4.3 原资源丢失转人工

删除 `restoreOriginalAttempt`、`BindRecovery` 及 SessionRebindable/旧写者缺席→新资源绑定的恢复路径。resume、reply、message 只允许在仍存在且身份吻合的原资源上继续；它们不能创建新 Attempt、owner、终端或替代 session。创建第一次资源的正常准备不属于资源丢失恢复。

已保存的原 final/回执即使资源丢失仍可补收。若这些事实足以完成当前业务结算，可记录结论；若下一步需要输入而原资源不可用，则停止自动推进。业务已明确未完成或用户等待不自动解除。

本轮复用 `status=blocked`、`phase=manual_intervention_required` 和现有 diagnostic 表达待人工，不新增顶层 `needs_attention` 枚举、人工处理状态机或自动重试命令。无法核实资源不等于资源已消失；短暂断线继续现有有界只读重连，现有预算耗尽或明确丢失后进入待人工。

创建/业务输入的未知结果只自动做一个有界只读对账窗口：使用尚未耗尽的原准备/命令期限，未有共同期限时本次自动查询最多 30 秒；窗口结束仍未知即持久化待人工。轮询及重启不为已经待人工的 Run 重开窗口。已明确 accepted 且 ResourcePending 的正常准备沿原准备期限，已开始的长模型回合也不受这个 30 秒限制；正常活动执行的 final 暂不可见不等于资源丢失。stop/close 的原结果核实及证据范围保持，本条不将未知停止结果改成成功，也不重发停止动作。

### 4.4 显式 resume 的人工对账出口

进入 `blocked/manual_intervention_required` 时设置 `ResumeRequired=true`、暂停新业务输入，保留原操作/授权来源、业务游标及已有结果。待人工状态允许纯查询、显式 resume，以及对仍可定位原资源的 stop/close；迟到只读事实不能自动解除人工阻断。

1. CLI 的 resume 受理与 `Controls.CanResume` 对该技术待人工状态开放，即使仍有 unknown；保留 request_id/正文幂等、expected_revision、未关闭及无 PendingStop 等控制准入。不能沿用现有“unknown 则受理前拒绝”的规则，使用户没有触发对账的入口。其他业务动作仍不能绕过 unknown；stop/close 撤销和终态优先。
2. 命令持久受理后，先在锁外执行一次有界原操作只读对账，总查询窗口最多 30 秒，包含等待/重连/读取。只使用已保存的原操作 ID、输入、资源和 session 绑定，调用原 Reconcile/观察能力；不调用 Execute，不新建 owner、Attempt、终端或替代 session，不为对账补做业务。已有明确终态事实直接复用，不重复查询。
3. 依原事务保存核实的回执和迟到 final，再复核最新 revision/原绑定、停止/关闭、源及业务资格。unknown 只能被真实原回执解决；仍未知、资源不可达、冲突或超时则保持待人工，本次 resume 的 action_status=failed 并返回具体诊断，不授权下一步。
4. 原事实已解决 unknown 且原资源身份有效时，显式 resume 才可在业务事务内解除该技术暂停。原回合仍活动则只接回其观察；原资源 idle 时仅继续尚未派发且来源有效的唯一后继。没有下一业务输入也可结算原完成事实；需要输入但资源丢失则仍待人工。它不自动解除业务 blocked/waiting_input，也不恢复 stop/close 撤销的授权。
5. 重放同一 request_id 只找回原命令；失败后用户可用新 request_id 和当前 revision 再试一次只读对账。服务中断时允许已有控制命令重新读取同一原事实，接受重复只读，不增加持久查询预算账本；成功续行和后继仍按原事务/操作去重。普通轮询不为已完成的人工对账命令另开窗口。

必须覆盖“原输入已接受、自动窗口先耗尽、回执随后可读、用户 resume 对账成功并继续原 Run”以及“仍未知可再次人工重查”两条公开 CLI 路径，不能依赖恰好仍存活的 observer 解除 unknown。

诊断使用现有公开字段给出 Run、工作区/分支、session/terminal、原动作 ID、已知结果和具体缺口；无值则省略，不猜测。人工继续可在原工具界面完成，或由用户另行决定新任务；本轮不提供自动复用旧工作区的快捷入口。

### 4.5 删除与保留

删除 `service verify-takeover --candidate` 的 CLI 路由、宿主转发、候选执行和逐 codec 兼容评估；旧命令按普通未知命令/exit 2 拒绝且不隐式启动服务。capabilities 不再发布该命令及跨构建恢复能力，客户端/helper/skill 不再调用；不保留返回假 compatible 的兼容壳。

删除仅服务退役开发 sandbox/旧 broker/profile/state 的分类、只读停止 adapter、解码器及测试。新 v7 只保留当前开发 full_access 和实际仍用的内容 read_only 编码；多个当前机制可能各有一个编码，不要求全局统一常量。删除 legacy `--add-dir` 载体前，把仍用于 worktree/common-dir 身份核对的路径改为直接路径值，不把路径归属检查一并删除。

保留当前有效的请求校验、非法 access_mode 拒绝、原生输入/结果身份、模型/effort、当前 owner/checkpoint 编码、精确停止及其证据范围、日志访问租约。capabilities 简单声明普通重启支持、资源重建不支持及升级排空约定，不再发布可接管版本组合清单。

## 5. 实现职责收口（PES-03）

### 5.1 职责表

| 所有者 | 负责 | 不承担 |
| --- | --- | --- |
| Workflow | 冻结步骤、提示词/模型角色、获取与业务核验条件、下一业务步骤 | 原生准备顺序、私有回执、资源重建 |
| application | 受理/幂等、Run gate、授权、原子提交、业务与标准执行事实协调；允许一个集中组装入口 | 在多个业务协调入口分散解释私有 codec、权限参数及原生历史 |
| reliable/operation | 通用准备顺序及发送前资格复核、已提交副作用身份、首次派发与原操作对账、去重/冲突和结果归属 | 后端私有 helper/control 准备细节、多版本恢复策略 |
| adapter | 当前有效 profile 冻结/校验、原生准备事实及私有细节、问答路由、输入/历史/final、workspace checkpoint、文件访问、停止及标准事实转换 | 下一业务步骤、自动恢复授权、直接修改 Run/DB、复制共享准备门禁 |
| host/组装入口 | 静态选择具体实现，单 writer、既有实例/资源身份 | 逐步骤业务路由、另一套状态推进或逐 Run 构建门禁 |
| storage/runstate | 当前格式记录、事务与公开事实 | 旧私有 codec 兼容、加载时生成新授权或后继 |

### 5.2 调用面与删除要求

1. 不以 application 零具体 adapter 导入为目标。允许 host/cmd，或 application 内一个明确登记的集中组装文件，直接选择具体实现；其他业务协调入口通过实际需要的能力调用。依赖守卫仅对该登记文件放行，不能把任意业务/私有解码代码塞入组装入口规避边界。
2. 复用已有 `LifecycleResolver` 及真实使用的窄端口。确需增加 profile 冻结、问答解码或文件源端口时，只传原有纯值、身份及必要选项；禁止传入整个 Record、Engine、Store、事务/提交回调或可选任意脚本。adapter 不反向导入 application/runstate/storage/workflow。
3. 对 `freeze` 的具体 profile/helper 构造、`policy.go` 权限构造、`control.go` 问答解码、`workspace_source.go` checkpoint、progress/result 文件源逐项评估。优先选择一项确有跨层修改或重复私有解释的能力，收口后删除原分支，再评估下一项；不强制一次搬完，也不为已集中的 native-viewer 选择再造包装。业务来源、审计条件和 PR 核验仍留在原业务所有者。
4. 保留 `reliable.Next` 的通用 workspace/resource/session 顺序，保留与 `QualifyAction` 共用的准备门禁及发送前复核；本轮不把它们搬回各 adapter。adapter 提供私有机制事实和具体执行。候选生成无创建/发送副作用，真正创建/输入仍先经原 operation 意图提交，再 Execute；已有意图只 Reconcile。不得将 create/send 隐藏到查询方法中。
5. 删除 `BindRecovery`、SessionRebindable 和仅服务旧接管的 codec/版本列表。原 `LifecycleRecoveryPort` 如仍承载原资源只读资格检查，可收缩后保留；不为改名字强制新增端口。保留共享准备 capability，不能将“删接管矩阵”扩大为删除发送前门禁。
6. 保留 Execute/Reconcile、观察、原资源停止及工作区/文件等实际能力。无需强行合成四方法大接口，也不按文件行数、包数量验收；不用一套全新 Runtime 框架替换现有正常主链。
7. 新增 helper/控制准备细节停留在 adapter 内，不增加共享生命周期动作；已有外部资源创建意图不可为减少字段而隐藏或自动重放。不新增第二个可靠性账本、通用队列、动态注册器或第二业务游标。

执行状态可在读取侧汇总为已接受、运行、完成、失败或待人工；不得以这些简化标签替代操作是否可能发生、业务完成和资源停止的原事实。

## 6. 快速定向验证（PES-04）

组件反馈使用现有 `go test <受影响包> -run <明确模式>`；受控闭环使用现有 `test-foundation.ps1 -Pattern <明确模式>`。不强制先跑完整 L1/Controlled，也不为此新增包依赖推导或缓存证明平台。

在 `scripts/test.ps1` 增加显式 `-Focused`，只接受单一 L2 或 L3、非空显式 Scenario、当前 Config、固定 RunnerExe 及新 OutDir；拒绝混合级别、通配全目录、PrerequisitesFrom、ListAvailability 和自定义 Catalog。复用原 catalog/case、配置评估、fixture、scheduler、lease、driver 与收尾，不复制真实测试实现。

Focused 跳过完整 L1/Controlled，仍新编译 native driver 并执行零匹配保护，记录实际 Runner/driver SHA、源码 commit/dirty、选择与实际执行 case、耗时、退出码和资源收尾。RunnerExe 须有匹配当前生产输入的现有构建回执；源码变化时重新构建，不引入新签名、阶段缓存或跨主机证据协议。

报告沿原 schema 加 `validation_scope=focused`，默认入口为 `complete`。Focused 仅能表达本轮选定 case 的 passed/failed，所有 complete_level_passed、baseline.*_verified 及完整交付资格为 false；即使选择覆盖某级全部 case 也不自动晋级。最终消费者/汇总须识别该字段，不能按退出码或数量给完整资格。

默认 test.ps1、现有 L2 前置复用和交付包完整入口保持自身资格规则；新的状态/恢复契约使旧场景退役时，应同步移除实现、catalog/case 注册和资格声明，不能保留必失败测试或以 skip 冒充通过。日常不为同一局部修改重复跑完整前置。快速验证批次按其脚本/合同及实际定向接线验收，不以恢复删除、v7 或全后端改造完成为前提；共享存储/控制改造的完整受控回归归该改造所属批次。

## 8. 独立交付与收益指标

一份文档管理四批，不等于一个不可拆分的发布。每批独立提交、验收并形成可交付结果；可以形成独立 PR，合并/部署仍按实际授权执行。后批失败或暂不实施，不撤销前批已完成的结论。共享完整检查按实际改动归属执行，不为每个局部修改重复整套验证。
